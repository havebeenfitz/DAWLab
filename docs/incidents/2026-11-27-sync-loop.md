# 2026-11-27: two apps kept waking each other into sync

## Summary

With hub change events (v1.7.0), two members of the same shared folder who had DAWLab open at the same time synced every ~2 seconds, nonstop, through every project of the folder. Both banners stayed on "Syncing ..." and restarting the app did not help. Each loop round costs a full folder sync on every Mac in the loop (log, filemaps, missing objects, log write for each project), so the hub's bandwidth grows with collaborators times projects times rounds. With more collaborators every change event fans out to everyone, so one loop wakes the whole folder.

## Timeline (Europe/Madrid)

- 13:30 v1.7.0: polling replaced by `GET /api/space/events`. The hub announced every successful `PUT log` as `versions`.
- 17:00 Collaborator stuck on "Syncing holding_pattern...". Hub checked: all requests fast, nothing missing.
- 17:07 Hub fix a3f0336: a log write that changes nothing is not announced. Loop continued.
- 17:27 Screen recording: the owner's app also cycles through all projects every ~2 s. `lastSync` in spaces.json confirms.
- 17:30 Hub fix e97bb50 deployed. No change events in the next two 2-minute windows, one sync per real change. Resolved.

## Root cause

Every sync writes each project's log to the hub (`PUT log`), whether or not it has new versions. Two Macs never hold byte-identical logs: top-level details (`metadata`, `bpm`, `key`, `primaryFile`, `ignoredFiles`) are computed per Mac, and commits with the same timestamp can be ordered differently. The hub's merge lets the incoming side win, so each write flipped those details back to the writer's values. The hub treated any difference as new versions and sent `versions` to the other member, whose sync wrote its own values back, which was announced to the first member, and so on.

a3f0336 only skipped byte-identical writes, so it did not break the loop.

## Fix

- Hub (e97bb50): a log write is announced, and bumps the project's `updatedAt`, only when the set of versions changes: commit ids per branch, their previews, and dismissals (`versionsKey` in `server/src/project-routes.ts`). Other details are still stored, silently.
- App (v1.8.0): every hub request has a 60 s deadline, file transfers fail after 90 s without bytes, and a failed sync retries with backoff (30 s up to 30 min). A hung request can no longer hold "Syncing" forever.
- Test: `server/src/__tests__/events.test.ts` writes logs that differ only in per-Mac details from two members and expects no event.

## What it costs as the folder grows

Each app runs at most one sync per folder at a time and queues at most one more (`requestSpaceSync` in `electron/sync/auto-sync.ts`), so one app's load is bounded, but it never stops. With **E** editors online and **P** projects in the folder:

- **Per app:** a folder sync back to back. Each one is `GET /space`, a `GET` and a `PUT` of each project's log, and the new-version check that every event triggers. With P = 5 that was about 11 to 17 requests per sync, every ~2 s, so 5 to 8 requests/s per open app, or around half a million a day.
- **Hub writes:** before the fix every `PUT log` rewrote `log.json` and the project's `meta.json`, about P per sync per editor.
- **Event fan-out:** each `PUT log` goes to every other member's streams (up to 3 per member), so events grow with E × (E − 1) × P, quadratically in editors. Listeners don't write logs, but they get the events and sync (reads) as well.
- **On every Mac:** network, CPU and battery all the time, and a folder that never reads as synced.
- **Silent:** nothing fails. Requests answer fast, nothing is logged, and answer times look normal. A hub on a metered plan pays for it without anyone seeing it.

## How to spot it

- A folder banner that never leaves "Syncing ..." while another editor has DAWLab open.
- The folder's `lastSync` in `~/.dawlab/users/<user>/spaces.json` changing every few seconds.
- `change` events with no new versions behind them on `GET /api/space/events`. A stream never gets its own member's changes, so watch it with one member's token to see the other member's events.
- Every project's `updatedAt` in `GET /api/space` moving together, within half a second, on each sync.

## Follow-ups

- [x] Force stop: when a folder's syncs keep restarting (6 starts within a minute) or one sync shows no progress for 2 minutes, the folder banner says so and offers **Force stop**. It pauses that folder's automatic syncs, retries and event-driven syncs until **Sync now** (`electron/sync/sync-guard.ts`, `forceStopSync` in `electron/sync/auto-sync.ts`). The button is not shown otherwise.
- [ ] The app sends a log only when it has something the hub lacks: the same versions key on the client, so an older or broken hub can't loop either.
- [ ] A convergence test with two editors and a listener against one in-process hub, events wired. It asserts that everything goes quiet (no events, no syncs) within a few rounds.
- [ ] A floor on event-driven syncs: at most one event-triggered folder sync per folder every N seconds, as a safety net.
- [ ] Visibility: the hub warns when a space sends more than a threshold of `change` events per minute, and the app records why each sync ran (start, save, event, retry, button). During this incident nothing showed what started the owner's syncs at 17:10, 17:11 and 17:13.
- [ ] After e97bb50, `interlude`'s `updatedAt` still moved once (17:25:34 to 17:32:24) with the owner's sync and no new version. Find which part of the versions key differed.

## Rules for the future

1. An event is sent only for a change another member must act on. Never for a write that merely restates state.
2. Anything a sync writes on every run must be idempotent on the hub, including when two Macs disagree on details. Test with two members writing different details back to back.
3. A client must never react to an event by writing something that produces an event, unless that write carries new data.
4. Before shipping a push mechanism, run two apps against one folder for a few minutes and watch the event stream and `lastSync`.
